# Postmortem: double charge on ORD-100953

## What happened
Victor Tanaka reported in #support that order ORD-100953 (Backpack, $59.00) was charged twice. Cause, per the Fixer: the payment service retried a charge after a timeout without an idempotency key. A timeout can come after the money has already moved, so each retry charged again.

## Who was affected
Investigator (read-only check of the payments database): 313 customers were double charged, $21,607.00 USD in total. 1 complained; 312 had not said anything yet. The biggest overcharges were $149.00 (for example CUS-2143, ORD-100052).

## The fix
`charge_order` now sends the same key (`charge-order:<order_id>`) on every attempt, and the provider returns the original charge for a key it has already seen. Committed on fix/double-charge (968df2f). Regression test `test_timeout_then_retry_charges_the_order_once` fails on the old code with 2 charges; pytest: `14 passed, 1 warning in 0.51s`. Approved by user.

## Refunds and emails
Batch `rb-da973e02dfbf` (313 customers, $21,607.00) was prepared at user's request and approved by user in #finance-approvals. Treasurer: 313 refunds, $21,607.00 in total. It sent 313 apology emails worded from the room document "apology-email", whose wording user approved.
